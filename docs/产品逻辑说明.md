# 中辉仓储订货咨询系统 — 产品逻辑说明

> 本文描述系统当前实际实现的业务逻辑，依据代码而非设计稿撰写。
> 对应代码版本：`5b79615`（2026-08-30）

---

## 一、系统定位

中辉物流为上游客户（如引能仕 OEM016）提供仓储代管服务。客户的货存在中辉仓库里，
客户的下游经销商（收货单位）需要提货时，先通过本系统**咨询**能不能订，
系统按实时库存判定，通过则**冻结**库存，实际发货后再**结转**扣减库存，
月末导出与手工台账同版式的《进出库明细》交付客户对账。

系统分两端：

| 端 | 入口 | 使用者 | 职责 |
|---|---|---|---|
| 前台 | `/` | 客户 / 业务员 | 提交订货咨询、查看咨询历史 |
| 后台 | `/admin` | 中辉内部管理员 | 基础数据维护、入库登记、发货结转、报表导出 |

后台登录：用户名密码配在后端 `.env`（`ADMIN_USER` / `ADMIN_PASS`），
签发 HMAC-SHA256 签名的 token，有效期 24 小时，存于 localStorage。
服务端每次请求校验签名与过期时间，过期后前端自动清除本地凭据并跳回登录页。

技术栈：React 19 + Vite（前端）、Express + MySQL 8（后端）、智谱 GLM（Excel 智能解析）。

## 二、核心概念：库存的三个量

理解整个系统的前提，是分清这三个数：

| 概念 | 出处 | 含义 |
|---|---|---|
| **库存（结存）** | `zhcc_product.stock_qty` | 仓库里实际有多少货 |
| **冻结** | `zhcc_stock_freeze` 中 `status='active'` 的 `freeze_qty` 之和 | 已被咨询占用、但还没发货的量 |
| **可用结余** | `库存 - 冻结`（实时算出，不落库） | 还能接多少新订单 |

### 关键规则：冻结不扣库存

这是最容易误解的一点：

```
咨询确认  →  写 zhcc_stock_freeze(status='active')   【不动 stock_qty】
一键备份  →  freeze 转 shipped + 扣减 stock_qty + 写 zhcc_product_backup 快照
```

也就是说，货没真正出库前，`stock_qty` 一直不变，只是「可用结余」变小了。
只有管理员执行「一键备份」（代表这批货确实发出去了），才真正扣库存。

### 冻结状态机

| 状态 | 含义 | 触发 |
|---|---|---|
| `active` | 已冻结，未发货 | 咨询确认时写入 |
| `shipped` | 已发货，库存已扣 | 一键备份时转换 |
| `released` / `completed` / `cancelled` | 表结构预留，当前流程未使用 | — |

## 三、前台：订货咨询

### 3.1 两阶段提交

咨询**不是**一次性提交，而是「先预演、再确认」两步，避免误操作占用库存：

```
第一步  POST /api/inquiry            → 只算不写库，结果暂存内存 10 分钟
        ↓ 用户看到每个商品能不能订
第二步  POST /api/inquiry/confirm/:batch_id  → 写咨询记录 + 冻结库存
   或   POST /api/inquiry/cancel/:batch_id   → 丢弃暂存，什么都不留
```

暂存批次放在后端进程内存（`pendingBatches` Map），**10 分钟自动过期**。
过期后确认会报「咨询批次不存在或已过期」，需重新咨询。

> 注意：暂存在内存意味着后端重启会丢失所有未确认批次；多实例部署时也无法共享。
> 当前是单实例部署，尚不构成问题。

### 3.2 整批判定，不拆单

一次咨询可以勾选多个商品。判定规则是**全有或全无**：

- 逐个商品算 `可用结余 = 库存 - active冻结`，`可用结余 >= 订货数量` 即该商品通过
- **只有全部商品都通过**，批次才算通过（`batch_result = 'approved'`），才执行冻结
- 只要有一个商品不足，整批判定为不可订，**一个都不冻结**

即使批次整体失败，确认后仍会为每个商品写一条咨询记录（留痕），
只是 `result` 分别标记通过/不通过，且不产生任何冻结。

### 3.3 两种下单方式

**手工选择**：选客户 → 选收货单位 → 勾商品填数量 → 提交。

**Excel 上传**（`POST /api/inquiry/excel/parse`）：直接传客户发来的订货单，系统自动解析。
这条链路依赖两样东西：

1. **解析规则**（`zhcc_excel_parse_rule`）：后台按客户预先配好，告诉系统去哪读数据
   - `downstream_name_cell`：收货单位在哪个单元格（可配多个补充单元格）
   - `product_code_start_cell`：商品编号从哪一格开始往下读
   - `quantity_column_offset`：数量列相对商品编号列偏移几列
   - `end_marker`：读到含此文本的行停止（默认「合计」）
   - `empty_value_treat_as_zero`：数量为空按 0 还是按无效
2. **智谱 GLM 模型**：把 Excel 里五花八门的收货单位写法（可能跨多格、带地址电话）
   匹配到系统已有的收货单位上。模型返回 JSON，包含匹配到的 ID、置信度、是否新建。
   **模型调用失败或返回非 JSON 时降级为「新建收货单位」**，不阻断流程。

商品匹配则是纯字符串精确匹配（按 `customer_product_code`），匹配不上的进
`unmatched_items` 返回给前端提示，不会静默丢弃。数量为空或 0 的行直接跳过。

### 3.4 咨询历史

前台可分页查看历史咨询记录，只读。页面上只暴露了**月份**筛选（默认当月），
接口本身还支持按客户、具体日期筛选，前端未使用。

## 四、后台管理

### 4.1 客户管理

上游客户（货主）的增删改查。客户编号唯一。

**新建客户时会自动创建一条「默认分类」**（见 4.4），保证后续建商品有兜底归属。

### 4.2 收货单位管理

下游经销商，按客户隔离。前台咨询时选择，导出报表时作为出库列的列名。
Excel 解析时若模型判断为新客户，会自动创建。

### 4.3 商品管理

商品是「仓储商品号 ↔ 客户商品编号」的对应关系载体，`warehouse_code` 全局唯一。

页面支持行内编辑、按客户/类别筛选、关键词检索。

**建档时手填的初始库存 = 期初结存。** 新建商品会同步写一条
`zhcc_product_backup` 记录（`remark='建档期初'`）——这一步很关键，因为
导出报表的期初结存列**只认这张备份表**，不补这条记录的话，商品在报表上
期初为空、整行结存链算下来全是 0，手填的库存完全不体现。
结存填 0 也照样写，0 是有效的期初值（就是没货），不是「没有期初数据」。

编辑商品时若发现它在备份表里一条记录都没有（历史遗留数据），会补一条建档期初兜底。

**手工改动结存会写一条「库存调整」快照**（`remark='库存调整 100 → 130'`），
既留下可追溯的痕迹，也让报表期初跟上当前库存。结存没变则不写。
注意副作用：快照按当前时刻落库，而期初取的是「截止次月 1 日的最近一次备份」，
所以**月中调整会让本月报表的期初变成调整后的值**。若要精确的月度账，
库存变动应尽量走入库单而非手工改。

### 4.4 商品分类

**按客户隔离**：每个客户一套自己的类别，互不可见。

每个客户恰好有一条 `is_default=1` 的「默认分类」，**不可删除**，
它是商品失去类别归属时的兜底去处：

- 新建商品未指定类别
- 商品改挂到别的客户，原类别不属于新客户
- 类别被删除，其下商品自动回落

**排序**：`sort_order` 由用户维护（值小的在前），相同时默认分类优先、再按名称。
这个顺序会同时作用于：商品管理列表、前台咨询商品列表、导出明细的分类分块、类别下拉。
各处都是「分类顺序在前 + 各自原有排序条件在后」（如商品管理页仍按仓储商品号二次排序）。

维护入口在商品管理页的类别下拉里——展开后第一项「全部类别」右侧的「管理」按钮。
类别筛选只在选定客户后可用（跨客户没有通用的类别表）。

### 4.5 入库管理

登记到货：商品、入库日期、入库数量、不良品数量、备注。

`实际入库 = 入库数量 - 不良品数量`（不能为负）。导出报表的「入库」列取的就是这个净值。

**入库会即时增加库存**，且增删改三种操作都会同步调整 `zhcc_product.stock_qty`：

| 操作 | 对 stock_qty 的影响 |
|---|---|
| 新增入库单 | `+ 实际入库` |
| 修改入库单 | 先 `- 原实际入库`，再 `+ 新实际入库` |
| 删除入库单 | `- 实际入库` |

整个过程在事务内完成。

`stock_qty` 一共有三个变更入口，入库是其中最主要的一个：

| 入口 | 方式 | 留痕 |
|---|---|---|
| 入库管理（本节） | 增量加减，`+/- 实际入库` | 入库单 |
| 一键备份（4.7） | 减量，`stock_qty - 本次发货量` | 发货快照 |
| 商品管理手工编辑（4.3） | 直接赋值 | 「库存调整」快照 |

### 4.6 咨询记录管理

按批次分组展示，展开可看批次内每个商品的明细（订货量、当时库存/冻结/可用、判定结果）。
支持按月份、客户、收货单位筛选，分页。

> 页面当前为**只读**。后端提供了 `DELETE /inquiry-records/:id`（逻辑已修正：
> 连带删除关联冻结、不动 `stock_qty`、已发货的记录拒绝删除），但前端未接入，
> 页面上无法触发。若要开放删除入口，接口已经可用。

### 4.7 一键备份（发货结转）

这是把冻结转为实际出库的操作，代表「这批货确实发出去了」，也是库存真正被扣减的时点。

```
1. 列出候选：freeze_date < 本月1日 且 status='active' 的冻结，按咨询批次分组
2. 管理员勾选要结转的批次/商品
3. 对选中项：
     freeze 转 shipped
     product.stock_qty -= 本次发货量
     写一条 zhcc_product_backup 快照（stock_qty=扣减后余额，frozen_qty=本次发货量）
```

**截止线是「本月 1 日」**——只结转上月及更早的冻结，本月的先挂着。
这与月度对账周期一致：本月的出库要留在本月报表里。

`zhcc_product_backup` 这张表有双重身份：既是发货快照，
也是导出报表**期初结存**的唯一数据源（取截止月末之前最近一次备份的 `stock_qty`）。

### 4.8 导出进出库明细

复刻客户手工台账《N月XXX进出库明细.xlsx》的版式。选客户即可导出，
**固定导出当前年月**（页面无年月选择；接口仍支持显式传参补导历史月份）。

**表格结构**：

| 列 | 内容 |
|---|---|
| A–G | 序号 / 仓储产品编号 / 客户编号 / **产品分类** / 客户产品代码 / 产品名称 / 规格 |
| H | 期初结存（上月末余额，**不参与**结存公式链） |
| I 起 | 按当月发生业务的日期横向展开，每个日期块 = `[入库][收货单位1..N出库][结存]` |
| 末行 | 合计行，H 列起每列纵向求和 |

**数值口径**：

- 入库 = `stock_in_qty - defective_qty`（净入库，不良品不单列）
- 出库 = `-request_qty`（记负数）
- 结存列是 Excel 公式 `SUM(上一个结存列 : 本块结存列的前一列)`，逐块累加

**排版细节**：

- 商品按「分类 → id」排序，同分类的行在 D 列**合并单元格**
  （排序是合并成立的前提，分类内部仍是 id 序，与手工表一致）
- 当天有几家收货单位发货就生成几列
- 冻结 A–G 列 + 前 5 行；自动筛选挂在第 5 行，合计行不纳入筛选区

**期初结存来源**：`zhcc_product_backup` 中 `backup_date < 次月1日` 的**最近一次**备份。
查不到记录则该列留空——刻意不兜底成 0，因为「数据缺失」和「期初确实为 0」
是两回事，把缺失显示成 0 会错误地表示无库存，比留空更危险。

**出库列只统计 `active` 冻结**，这点容易误解：一批货一旦经一键备份转为 `shipped`，
它就从出库列里消失了。这不是 bug，而是避免重复计算——

```
已发货(shipped)：库存已扣 → 已反映在「期初结存」里 → 不再单列出库
未发货(active) ：库存未扣 → 作为本期出库列出，参与结存公式
```

换句话说，期初结存承载的是「已结转的历史」，出库列承载的是「尚未结转的当期发生额」，
两者相加才是当前实际可支配的量。

## 五、完整业务链路

一件货从入库到出现在报表上的全过程：

```
① 入库登记        写 stock_in 记录，实际入库 = 入库量 - 不良品
                  stock_qty += 实际入库

② 客户咨询        算 可用结余 = stock_qty - active冻结
                  整批全通过才算通过，结果暂存 10 分钟

③ 确认冻结        写 inquiry_record + stock_freeze(active)
                  【stock_qty 不变】，但可用结余变小

④ 一键备份        （月初操作，只处理上月及更早的冻结）
                  freeze 转 shipped
                  stock_qty -= 发货量
                  写 product_backup 快照

⑤ 导出报表        期初结存 ← product_backup 最近一次快照
                  入库列   ← stock_in 净入库
                  出库列   ← inquiry_record ⋈ stock_freeze(active)
                  结存列   ← Excel SUM 公式逐块累加
```

## 六、设计说明与遗留事项

### 6.1 出库列为什么会出现往月的日期块

导出时出库数据的查询**只有上界**（`inquiry_date < 次月1日`），没有下界，
所以历史上任何仍处于 `active` 的冻结都会持续出现在每个月的报表里
——4 月、7 月的日期块出现在 8 月报表中就是这个原因。

**这是有意保留的行为**：未发货的冻结实实在在占着库存，让它一直挂在报表上
可以起到提醒作用，直到被一键备份结转（转 `shipped`）后才从出库列消失、
转由期初结存承载。

代价是同一笔未结转的出库会在多个月的报表里重复出现。
要避免这种情况，应当按月及时执行一键备份，而不是改查询条件。

### 6.2 未确认咨询批次存在内存

暂存批次放在后端进程内存的 `pendingBatches` Map 里，10 分钟过期。
后端重启会丢失所有未确认批次，多实例部署时也无法共享。
当前单实例部署，尚不构成问题；若要横向扩容需改为 Redis 或落库。

### 6.3 无操作审计

后台账号是 `.env` 里的单一固定账号，无角色区分。各表虽然都设计了审计字段
（`create_user_id`、`create_fullname`、`update_user_id` 等），但代码从未写入，全为 NULL。
要启用需要先有真正的用户体系。

以下问题曾存在于代码中，现已修复，保留记录以备回溯：

| 问题 | 原表现 | 修法 |

| 咨询记录删除接口不可用 | 引用了不存在的字段（`rec.freeze_qty`、`inquiry_record_id`），回退分支永不执行，删完留下孤儿冻结、库存被永久占用；且逻辑反向（下单未扣库存却要加回） | 重写：连带删除关联冻结、不动 `stock_qty`、已发货记录拒绝删除。前端仍未接入，页面保持只读 |
| 手工改库存不留痕 | 商品管理页直接赋值 `stock_qty`，无流水、报表期初也不同步 | 结存变动时写一条 `remark='库存调整 X → Y'` 的备份快照 |
| 删除商品残留孤儿 | 只删 `zhcc_product`，备份快照与冻结记录成为孤儿，孤儿 `active` 冻结继续占用可用量 | 事务内连带清理 `zhcc_product_backup` 与 `zhcc_stock_freeze`（入库单、咨询记录作为业务凭证保留） |
| token 永不过期 | `signToken` 写了 24 小时 `exp`，`verifyToken` 却只验签名不比对 | `verifyToken` 增加 `exp` 校验 |
| Excel 解析字段缺失 | `matchProducts` 返回 `product.warehouse_code`，但 SQL 未 SELECT 该字段，实际为 `undefined` | SQL 补上 `warehouse_code` |
| 401 跳转路径写死 | 硬编码 `/admin`，生产部署在 `/zhcc/` 子路径下会跳到 404（token 开始会过期后此问题才真正暴露） | 改为 `${import.meta.env.BASE_URL}admin` |

> 关于「手工改库存写调整快照」的一个副作用：快照按当前时刻落库，
> 而期初结存取的是「截止次月 1 日的最近一次备份」，
> 所以**月中做库存调整会让本月报表的期初变成调整后的值**（本应是上月末的值）。
> 这是选定该方案时已知并接受的权衡——相比之下，不留任何痕迹的风险更大。

## 七、数据表一览

| 表 | 用途 | 关键说明 |
|---|---|---|
| `zhcc_customer` | 上游客户（货主） | `customer_code` 唯一 |
| `zhcc_downstream_customer` | 收货单位 | 按 `customer_code` 隔离 |
| `zhcc_product` | 仓储商品 | `warehouse_code` 唯一；`stock_qty` 为当前实际库存 |
| `zhcc_product_category` | 商品类别 | 按客户隔离；每客户一条 `is_default`，不可删；`sort_order` 控制顺序 |
| `zhcc_inquiry_record` | 咨询记录 | 一行 = 一次咨询中的一个商品；`batch_id` 串起同批次 |
| `zhcc_stock_freeze` | 库存冻结 | `active` 占用可用量，`shipped` 表示已发货扣过库存 |
| `zhcc_stock_in` | 入库登记 | 净入库 = `stock_in_qty - defective_qty` |
| `zhcc_product_backup` | 发货快照 / 期初结存源 | 双重身份，见 4.7、4.8 |
| `zhcc_excel_parse_rule` | Excel 解析规则 | 按客户配置，`is_default` 标记默认规则 |

### 部署提示

数据库变更脚本 `database/migration_product_category.sql` 为**幂等**脚本，
可重复执行。它会建类别表、加 `category_id` 与 `sort_order` 列、
回填存量商品分类、补齐缺失的期初备份，末尾输出三项校验计数（都应为 0）。

**不要在脚本里写死库名**——各环境库名不同（本地 `zhcc_warehouse`、生产 `hitech`），
执行时用 `-D` 指定：

```bash
mysql -h<host> -u<user> -p -D <dbname> < database/migration_product_category.sql
```

上线顺序：**先跑数据库脚本，再部署代码。**
